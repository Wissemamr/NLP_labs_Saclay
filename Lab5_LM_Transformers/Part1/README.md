# Part 1: transformer language model

Implement and train a small decoder-only transformer to predict the next token
and generate stories. The lab asks for a short training experiment, together with
a description of the implementation choices and a conclusion in the notebook.
N.B: In our case we went up to 500 epochs to see how the loss and perplexity decrease.

## Dataset and selected examples

[TinyStories](https://huggingface.co/datasets/roneneldan/TinyStories) contains
synthetic short English stories generated by GPT-3.5 and GPT-4 using simple
vocabulary. Its training split contains approximately **2.12 million stories**;
the validation split contains approximately **22,000 stories**. Each example is
a story in the `text` field, rather than a single token or training batch.

The current notebook selects:

```python
TRAIN_EXAMPLES = 2000
VALIDATION_EXAMPLES = 32
```

`load_dataset(..., streaming=True).take(TRAIN_EXAMPLES)` selects the first 2,000
training stories without materializing the entire training split. The selected
stories are stored in a Python list, and the DataLoader shuffles this subset
using a generator seeded with 42. The subset selection itself is not random.
Validation uses the first 32 stories from the separate validation split.

Stories are tokenized with `mistralai/Mistral-7B-v0.3`, whose vocabulary has
32,768 tokens. Sequences longer than `MAX_LENGTH` are truncated; shorter ones
are padded to the longest sequence in their batch. The model trains on the
retained prefix of each story, which may be shorter than the complete story.

The next-token task shifts each tokenized sequence by one position:

```text
Input:   token_1, token_2, token_3
Target:  token_2, token_3, token_4
```

Thus a sequence of length `MAX_LENGTH` provides at most `MAX_LENGTH - 1`
next-token targets. EOS is reused as the padding token; the attention mask
identifies actual padding positions, whose targets are set to `-100` and
excluded from the loss. Real EOS tokens remain valid prediction targets.

## Current training settings

The first code cell selects CPU or CUDA automatically. The settings currently
saved in the notebook are:

| Setting | CPU | CUDA GPU |
| --- | ---: | ---: |
| Selected training stories | 2,000 | 2,000 |
| Selected validation stories | 32 | 32 |
| Batch size | 2 | 4 |
| Maximum sequence length | 64 tokens | 128 tokens |
| Maximum training steps | 500 | 1,000 |
| Available batches in one pass | 1,000 | 500 |
| Actual steps per training-cell run | 500 | 500 |
| Training stories processed per run | 1,000 | 2,000 |

A **step** processes one batch and performs one optimizer update. An **epoch**
is one complete pass through the selected training subset. The training loop makes up to `NUM_EPOCHS` passes (currently 1); it stops when
that many epochs finish or the global `MAX_STEPS` limit is reached:

```text
available batches = ceil(TRAIN_EXAMPLES / BATCH_SIZE)
actual steps = min(MAX_STEPS, NUM_EPOCHS * available batches)
effective epochs = sample presentations / selected training stories
```

For example, the CPU configuration processes 500 batches of 2 stories: 1,000
of the 2,000 selected stories, or half an epoch. The GPU configuration consumes
all 500 available batches, completing one epoch even though `MAX_STEPS=1000`.
`NUM_EPOCHS` controls complete passes; `MAX_STEPS` caps updates across all
epochs. Both limits apply. Repeated stories count again in sample presentations;
metadata separately records the number of unique selected examples seen.

Training uses AdamW with learning rate `6e-4` and gradient clipping with maximum
norm 1.0. Adjust these settings in the first cell, then run all cells:

```python
NUM_EPOCHS = 1
MAX_STEPS = 1000 if device.type == "cuda" else 500
TRAIN_EXAMPLES = 2000
VALIDATION_EXAMPLES = 32
EVAL_EVERY = 50
```

Increase `NUM_EPOCHS` and `MAX_STEPS` together to allow multiple passes. For
example, with 2,000 stories and CPU batch size 2, `NUM_EPOCHS=3` and
`MAX_STEPS=3000` allow three complete passes (6,000 sample presentations).

Each execution of the training cell creates a fresh model and AdamW optimizer,
resets the seed and training shuffle generator, and starts an independent run.
Changing only the generation prompt does not require retraining. The notebook
does not automatically resume training from a previous checkpoint.

## Model architecture

Architecture: vocabulary 32768, embedding 256, intermediate 512, 4 heads of
dimension 64, and 8 decoder blocks. Blocks use pre-RMSNorm, RoPE, causal masked
attention, and SwiGLU feedforward layers. Padding uses EOS but only padding
positions identified by the attention mask are ignored in the training loss.

## Results and interpretation

The training cell logs cross-entropy loss and perplexity for each batch. Individual values
fluctuate because batches contain different stories; look for an overall trend.
The generation cell reloads the saved model and prints a continuation of the
prompt. Both greedy decoding with a KV cache and sampling are implemented;
generation helpers expect unpadded prompt batches.

Validation is measured before training (step 0), every `EVAL_EVERY` updates,
and after the final update. Each evaluation uses the same validation subset.
The final cell displays the saved learning curves and validation results:

```text
validation loss = total negative log-likelihood / number of non-padding targets
perplexity = exp(validation loss)
```

**Lower validation loss and lower perplexity are better.** Perplexity is another
expression of the same loss, rather than an independent metric. Uniform
predictions across 32,768 tokens would give loss approximately 10.40 and
perplexity 32,768.

An earlier 10-step CPU verification run achieved validation loss **8.1099** and
perplexity **3327.30**. These are historical pipeline-check results, not results
for the current 500-step configuration. Generated text was repetitive after
that short run. More training is needed for useful story generation.

Compare experiments using the same validation stories, tokenizer, and sequence
length; changing these also changes what is being measured. The CPU and GPU
defaults use different sequence lengths, so align them for a direct comparison.
A 32-story validation subset provides only a preliminary estimate. If training
loss decreases while validation loss increases, the model may be overfitting.

## Timestamped runs and report artifacts

Every training-cell execution creates a new directory under `Part1/runs/`:

```text
runs/
  20261019_143000_123456_a1b2c3/
    metadata.json
    metrics.csv
    training.log
    model.pt
    tokenizer/
    sources.json
    learning_curves.png
    learning_curves.pdf
    generations.jsonl
```

Run timestamps use **Australia/Brisbane (UTC+10)**. Microseconds and a random
suffix prevent collisions. Existing runs are preserved; generated run folders
are ignored by Git. Copy the figures, values, and metadata you need into your
report archive explicitly.

| Artifact | Contents |
| --- | --- |
| `metadata.json` | Configuration, model dimensions, seed, device, library versions, selected subset sizes, batch/sequence sizes, configured epochs, actual effective epochs, steps, sample presentations, target tokens, runtime, status, initial/final validation results |
| `metrics.csv` | Training measurement at every update and periodic validation measurements, with step, epoch progress, loss, perplexity, sample/token counters, learning rate, gradient norm, and elapsed time |
| `training.log` | Progress messages, run location, completion message, and failure traceback if applicable |
| `model.pt` | Final model weights, architecture, optimizer state, step, training loss history, tokenizer ID, run ID, and CPU RNG state |
| `tokenizer/` | Tokenizer files saved with the run |
| `sources.json` | Snapshots of the notebook, RoPE implementation, and experiment helper |
| `learning_curves.png` / `.pdf` | Report figures with training/validation loss and perplexity versus optimizer step |
| `generations.jsonl` | Prompt, generated continuation, decoding settings, and timestamp for each execution of the generation cell |

CSV rows are flushed immediately and metadata counters are updated during
training. A failed or interrupted run retains its available metrics and a status
in metadata. The final checkpoint and figures are produced on successful
completion; a failed run is not a completed model checkpoint.

The training cell exports figures automatically. The last notebook cell displays
them inline. Training batch measurements are taken before each update;
validation measurements are taken after the indicated update, except step 0.
Perplexity uses a logarithmic vertical axis. Lines show measured values without
forcing a decrease or smoothing away fluctuations. Batch perplexity is
`exp(batch loss)`; averaging batch perplexities is not corpus perplexity.

To reopen an older run's curves in a notebook cell:

```python
from pathlib import Path
from experiment import plot_run

figure = plot_run(PART1_DIR / "runs" / "<run folder>")
plt.show()
```

To inspect saved metrics or compare runs manually:

```python
import pandas as pd

metrics = pd.read_csv(RUN_DIR / "metrics.csv")
display(metrics[metrics["split"] == "validation"])
```

The generation cell uses the just-completed run's `model.pt` and reconstructs
the architecture saved in that checkpoint. To generate from an older run, set
`RUN_DIR` to its directory and `CHECKPOINT_PATH = RUN_DIR / "model.pt"` before
running the generation cell. To resume training manually, both model and
optimizer states must be restored; the notebook's training cell intentionally
starts a new experiment. The saved CPU RNG state alone is not sufficient to
reproduce a resumed CUDA/DataLoader trajectory exactly.

The supplied `optimizer_state_dict_llama_mini.pth` and older `checkpoints/`
files are preserved and unused by the new run pipeline. The supplied file has
optimizer state, not pretrained model weights.
